## 2. 원인

1. **외장 SSD(APFS) 파일 시스템 손상** — 쓰는 도중 끊긴 흔적(`invalid o_xid … expected …`). 전원 차단·시스템 멈춤으로 추정. 재부팅 뒤 마운트가 거부돼 DB 데이터 폴더가 없었다.
2. **재부팅 뒤 컨테이너·망 상태를 배포가 못 알아챔** — 배포 스크립트는 "`stock_net` 에 붙어 있나"만 봤는데, `docker inspect` 는 멈춘 컨테이너도 '붙어 있음'으로 보여 준다. 그래서 자동 재연결이 돌지 않고 마이그레이션 단계에서 이름 해석 실패로만 드러났다.
3. **상용 CH 읽기 전용 터널(`stock_ch_ro_tunnel`)도 재부팅 뒤 안 뜸** — runbook 에 '재부팅 점검 목록에 추가'라고만 적혀 있었다.
4. (보조) 재부팅 직후 로그인 전에는 OrbStack·러너가 뜨지 않아 터널·배포가 늦게 살아났다.

## 3. 잃은 것 / 남은 것

- **잃음(개발 PostgreSQL 전부)**: 회원·게시판·게시글, 앱 버전·광고·기능 스위치·푸시 템플릿, 관리자 계정, 게임 시즌·기록, 개발 자체 CH(게임 분봉·시장 그룹).
- **남음**: 시세 데이터 — 개발 서버는 상용 CH 를 읽기 전용으로 읽으므로 다시 수집할 필요 없음. 코드·설정 파일(env)은 디스크 밖이라 무관.

## 4. 이번에 고친 것

- `deploy/swarm/preflight.sh`(배포 사전 점검): DB·터널이 **실제 실행 중**인지, healthy 인지, 같은 망의 임시 컨테이너에서 **이름이 풀리는지**까지 본다. 꺼진 컨테이너는 시작하고, 이름이 안 풀리는 연결은 다시 붙인다. 시작 실패(디스크 문제)는 이유·복구 문서를 알려 주고 멈춘다(옛 서비스 유지). bash 3.2·`set -euo pipefail` 에서 7가지 상황 시험.
- `single-node-swarm.md` 9절: 재부팅 뒤 복구 순서(디스크 → DB → 터널 → 망 → 배포 → 1회 초기화).

## 5. 재발 방지 — 고를 것

| 방법 | 효과 | 비용·주의 |
|---|---|---|
| **A. 매일 `pg_dump` 백업**(추천, 먼저) | 디스크가 또 깨져도 PG 설정·회원을 몇 분 안에 되살림. 이번 손실의 대부분을 막는다 | 백업 파일은 **다른 디스크**(내장 또는 클라우드)에. 크기 작음(개발 PG) |
| B. DB 를 내장 디스크로 옮기기 | 외장 연결·마운트 문제 자체가 없어짐 | 내장 여유 공간 필요(사용 26GB 수준). 볼륨 경로 변경·이동 작업 1회 |
| C. UPS(무정전 전원) | 정전·순간 전원 차단으로 인한 손상 예방 | 장비 구매 |
| D. SSD 교체 | 같은 SSD 가 다시 깨지면 하드웨어 고장 가능성 | 초기화 뒤 같은 증상이 반복될 때 |

- 상용 서버도 같은 Swarm+compose DB 구조다. 상용 재부팅 시험 전에 이 문서와 9절을 먼저 본다(상용 DB 볼륨이 부트 디스크인지 별도 디스크인지는 아직 확인하지 않았다 — 시험 전에 `docker inspect stock_postgres_prod` 의 Mounts 로 확인).
